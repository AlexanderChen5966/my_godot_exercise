## 1. 為什麼要調整

1.0 版的功能都已完成，但試玩後發現劇本本身有三個問題：

1. **選擇沒有後果**：幾乎每個選項都通往同一個下一場景。真正的分歧只有場景 17，而且是讓玩家**直接挑**結局。
2. **填充選項太多**：每個場景都有「停留不動」類的選項，場景 4 甚至有 3 個，玩起來像卡住。
3. **劇情重複**：場景 11～14 重演了 5／7／8／10 的事件（錄音筆、研究設施、逃脫、回家）。

## 2. 已決定的方向

| 議題 | 決定 |
|---|---|
| 快速結局（Bad End） | **加入**。觸發後可以「從這裡重試」（回到觸發前的場景），也可以回標題 |
| 最終結局怎麼決定 | **隱藏數值**（記憶、人性）決定能走向哪個結局，不再讓玩家直接挑 |
| 劇本由誰寫 | **Claude 起草，作者審稿定稿**（需修改 CLAUDE.md 的「Claude 不可改寫劇情」條款） |
| 重複的場景 11～14 | **改寫成新事件**，搭配新的背景圖、BGM 與音效 |
| 新素材 | **作者自行準備**；Claude 提供每項素材可直接使用的**生圖、BGM、音效提示詞**（見階段 B） |
| Bad End 畫面 | 所有 Bad End **共用一張新圖和一首音樂**，只有文字不同 |

## 3. 劇本結構提案（大綱層級，細節在階段 A 審稿時決定）

| id | 場景 | 變動 |

| 6 | 遭遇搜捕隊 | 「狂吼嘶吼」→ **BE1 槍聲** |

| 14 | **新**：女兒 | 遠遠見到女兒，比出手勢，呼應場景 15 的「手勢」和舊場景 14 的「你不會傷害我」 |
| 15–16 | 聽見／牆上的訊息 | 保留 |

**數值（暫定，大綱審稿時再調整）**
- 初始值：記憶 0、人性 3。
- 結局 A 需要記憶 ≥ 6 且人性 ≥ 3；結局 B 需要記憶 ≥ 3；結局 C 沒有條件。

## 4. 劇本格式 1.5（相容 1.0，舊欄位都不變）

```json
{
  "version": "1.5",
  "stats": { "memory": 0, "humanity": 3 },
  "scenes": [{
    "id": 6, "...": "...",
    "ending_type": "bad",            // 選填：normal（預設）／true／bad；只在 is_ending 時有意義
    "ending_label": "— 死亡結局 —",   // 選填：取代 EndingTag 的文字
    "choices": [
      { "text": "狂吼嘶吼", "response": "...", "next_id": 21,
        "effects": { "humanity": -1 } },              // 選填：數值增減
      { "text": "面對真相", "response": "...", "next_id": 18,
        "require": { "memory": 6, "humanity": 3 },   // 選填：最低門檻
        "locked_text": "……（你想不起來）" },          // 選填：未達門檻時顯示的文字
      { "text": "從這裡重試", "action": "retry" },    // 選填：retry／title，取代 next_id
      { "text": "回到標題", "action": "title" }
    ]
  }]
}
```

所有新欄位都是選填的；1.0 的劇本不需要修改，也能在新程式上照常運作。

## 5. 實作步驟

| 階段 | 內容 | 狀態 |
|---|---|---|
| A | 劇本：大綱 → 文字草稿 → 定稿寫入 JSON | 未開始 |
| B | 素材需求清單（可和 A 同時進行） | 未開始 |
| C | 程式：支援格式 1.5、擴充劇本檢查 | 未開始 |
| D | 素材整合（作者交付素材後） | 未開始 |

### 階段 A：劇本（兩個停止點，需要作者審稿）
1. 寫 `docs/story_v1.5_outline.md`：每個場景的事件、選項、數值效果、Bad End 觸發點，以及數值門檻試算（最佳路線和最差路線分別能拿到多少）。→ **停：請作者審大綱**
2. 依定稿的大綱寫完整文字草稿 `docs/story_v1.5_draft.md`，用 Markdown 方便閱讀和修改。→ **停：請作者審文字**
3. 定稿後轉成 `data/story.json`；1.0 版備份到 `docs/story_v1.0.json`。不放在 `data/` 是因為 Web 匯出的 include_filter 是 `data/*.json`，放在那裡會被一起打包。

### 階段 B：素材需求
- 寫 `docs/asset_requests.md`：
  - **背景 5 張**：`scene_21`～`scene_24.webp`（對應新的場景 11～14）、`bad_end.webp`。規格 1152×768，畫風要和現有 20 張一致，附畫面描述和 AI 繪圖提示詞。
  - **BGM 4～5 首**：ogg，會自動循環。附 AI 音樂生成提示詞（曲風、情緒、樂器、速度、長度、要能無縫循環）。
  - **選配音效**：例如槍聲、心跳。附 AI 音效生成提示詞（聲音描述、長度）。**要關掉循環**，因為專案預設 ogg 都會循環。
  - 每項素材都會附：檔名、用在哪個場景、畫面或聲音描述、**可以直接貼上的提示詞**（中文說明＋英文提示詞），以及格式規格（尺寸、檔案格式、長度）。
- 提示詞的時程：
  - **Bad End 的圖和音樂**跟劇情細節無關，可以最先給。
  - **場景 11～14 的新素材**要等階段 A 的大綱定稿，才知道畫面內容，所以在大綱審完後一起給。
- 素材交付前，JSON 先暫時指向現有的圖和 BGM；交付後只要改檔名。

### 階段 C：程式（`scripts/`、`tools/`）
- `scripts/story_data.gd`：讀取 `stats` 的初始值，沒有的話給空字典。
- `scripts/main.gd`，沿用現有的狀態機和函式：
  - 新增 `_stats`，在 `_start_game()` 重設成初始值。
  - `show_scene()` 進入非結局場景時存一份**檢查點**（場景 id ＋ 數值複本），給「從這裡重試」用。
  - `_build_choices()` 依 `require` 判斷是否鎖定；鎖定的按鈕設成 `disabled`，顯示 `locked_text`。
  - `_on_choice_pressed()` 套用 `effects`，並記下 `action`。
  - `_input()` 在 RESPONSE 狀態時：
    - `action == "retry"` → 還原檢查點，`show_scene(檢查點 id)`。
    - `action == "title"`，或 1.0 格式的 `is_ending` → 沿用 `_return_to_title()`。
  - `EndingTag` 的文字依 `ending_label`／`ending_type` 設定。
  - **除錯用的數值顯示**：只在 `OS.is_debug_build()` 時可以按 F3 顯示目前的記憶和人性，Web 正式版不會出現。
- `tools/validate_story.gd` 擴充：
  - `effects`／`require` 用到的數值名稱必須定義在 `stats` 裡。
  - `action` 只能是 retry 或 title；每個 Bad End 都要有 retry 和 title。
  - **窮舉所有路線**：確認每個結局（含 Bad End）都走得到，並算出最佳路線的數值，確保真結局達得到。
- 文件：
  - `CLAUDE.md` 的劇本規則改成「Claude 可以起草，須經作者審核定稿後才能寫入 story.json」，並更新劇本格式說明和「劇本之後可能再調整」一節。
  - README、PROMPTS 同步更新。

### 階段 D：素材整合
- 素材放進 `assets/bg/`、`assets/bgm/`、`assets/sfx/`。
- 音效的 `.import` 改成 `loop=false`，再用不帶參數的 `editor_refresh` 讓整個專案重新匯入。
- JSON 從暫用素材切換成新的檔名。

## 6. 驗證方式

1. `script_check`／`lsp_project_diagnostics`：沒有錯誤。
2. 劇本檢查（對拿掉外掛的專案副本執行）：格式正確；3 個結局和 3 個 Bad End 都走得到；最佳路線達到真結局的門檻。
3. headless 自動測試（專案副本）：
   - 最佳路線得到 A，中間路線得到 B，最差路線得到 C。
   - 觸發每個 Bad End 後，「從這裡重試」會回到觸發前的場景，數值還原成進場時的值；「回到標題」會回到標題並重設數值。
   - 場景 17 未達門檻的選項是 disabled，點了沒有反應。
4. MCP 實玩：`game_start` → 用 `execute_code` 設定數值並跳到場景 6／8／11／17 → `input_simulate` 點選 → `runtime_screenshot`（disk 模式）確認 Bad End 畫面、鎖定的選項、EndingTag 文字。
5. 作者試玩：文字是否通順、Bad End 會不會太突然、新素材和聲音是否合適。
6. 重新匯出 Web 版（用專案副本、排除 addons），在瀏覽器確認。
